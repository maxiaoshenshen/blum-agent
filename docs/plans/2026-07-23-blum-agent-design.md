# Blum Agent 产品与技术设计

## 1. 产品目标与验收边界

Blum Agent 是一个中文优先、面向全角色的百隆五金专家 Web 应用。它服务设计师、销售、安装工、生产、采购与消费者，并根据用户身份自动调整术语深度、回答结构和下一步建议。首版必须覆盖产品认知与选型、柜体方案、型号和配件关系、安装调试、故障排查、采购准备、客户沟通及使用维护等典型任务。

“回答关于 Blum 的一切问题”被定义为：对所有相关问题都给出有用且诚实的处理结果，而不是声称掌握不存在的信息。可核实的事实必须优先引用 Blum 官方来源；型号、尺寸、承重、孔位、兼容性和安全信息不能凭模型记忆下结论。信息不足时，Agent 应列出缺失参数、说明不确定性，并指向产品配置器、产品目录、EASY ASSEMBLY 或当地 Blum 联系渠道。

核心验收标准：

- 用户可以选择角色，也可以直接以自然语言提问。
- 回答包含结论、依据、可执行步骤、风险提示和来源。
- 支持图片随问题提交，用于识别产品、安装状态或故障线索。
- 无 API Key 时仍可运行演示模式，提供角色化引导和官方资料入口。
- 有模型配置时调用指定的 OpenAI-compatible Chat Completions 服务，并用本地维护的官方资料上下文约束回答。
- 桌面和移动端均可使用，键盘操作、焦点状态、色彩对比和动态效果符合基本可访问性要求。

## 2. 方案选择

评估了三种实现路径：

1. **纯通用大模型**：开发最快、覆盖面看似最大，但技术参数和型号兼容性容易产生幻觉，不满足专业场景的可信度要求。
2. **纯静态知识库 RAG**：官方资料可控、引用稳定，但更新需要持续同步，对新品、地区差异和长尾问题覆盖不足。
3. **混合专家系统（选定）**：本地结构化产品地图负责角色、意图和稳定导航；模型负责理解、组织与图片推理；官方资料索引负责提供可审计上下文。回答层强制输出来源和置信状态。

首版采用第三种路径。它不会在本地复制完整产品手册，也不会冒充官方产品配置器。对于精确 BOM、CAD、孔位和订购号，Agent 先收集必要参数，再给出可核实结论或将用户引导到官方配置器。这一取舍能在当前交付范围内实现最大覆盖，同时降低错误采购和错误安装的风险。

应用采用“任务入口 + 对话工作台”而非传统后台仪表盘：首页直接呈现六类角色与常用任务，用户点击后得到针对该角色的建议问题；主对话区持续显示来源、置信度和下一步。产品家族作为可筛选的知识导航存在，但不与聊天竞争视觉注意力。

## 3. 架构与组件

技术栈采用 Next.js、React、TypeScript 和全局设计令牌；测试使用 Vitest、Testing Library 与构建后 Worker 集成测试。服务端 Route Handler 代理模型请求，API Key 永不进入浏览器。客户端仅发送必要的对话消息、当前角色和可选图片，不采集姓名、联系方式或交易信息。

主要模块：

- `domain`：角色、产品家族、任务意图、官方来源与回答置信度的纯 TypeScript 模型。
- `knowledge`：稳定的 Blum 产品地图和官方入口，支持关键词检索与提示词上下文生成。
- `agent`：输入校验、对话截断、系统指令、模型响应归一化及错误映射。
- `app/api/chat`：服务端 API；存在 `PROVIDER_*` 配置时调用 OpenAI-compatible Chat Completions，不存在时返回明确标记的演示回答。
- `components`：角色选择、任务建议、对话消息、来源卡片、图片附件、输入编辑器和状态反馈。
- `app`：响应式产品界面、元数据、错误边界和静态说明页。

数据流为：用户选择角色并提交问题 → 客户端完成基础校验与图片压缩/格式检查 → 服务端重新校验 → 本地知识路由识别产品域和高风险意图 → 模型结合官方来源优先规则回答 → 服务端将内容、来源和置信状态归一化 → 界面分层展示，并保留继续追问所需的上下文。

## 4. 可信回答、异常与安全

Agent 的系统规则将事实分为三级：`verified` 表示本次回答有官方来源直接支撑；`guided` 表示给出方法和信息收集步骤，但未确认精确型号；`needs-review` 表示涉及安全、精确订货或资料冲突，需要人工或官方工具复核。界面不使用模糊的“AI 可能出错”代替具体风险，而是在对应结论旁展示原因。

以下情况不得直接给出确定结论：缺少柜体高度/宽度、面板重量或材质却要求选 AVENTOS 省力装置；缺少完整产品号却判断配件兼容；涉及承重、安全、防脱落、电气接线或开孔尺寸但没有官方依据；不同市场产品系列或编号可能不同。模型应先询问最少必要参数。

异常处理包括：空问题、超长问题、不支持的附件、图片过大、API Key 缺失、模型超时、限流、上游返回格式异常和网络不可用。用户看到的是可恢复操作，而不是堆栈信息。服务端日志不得记录图片正文、完整会话或密钥。

安全边界包括服务端环境变量、输入长度与图片类型限制、上游超时、最小化错误暴露以及外链 `noopener`。首版不实现账号、支付、报价承诺、订单提交或持久化客户数据，避免在缺少业务系统与权限模型时制造伪能力。

## 5. 测试、视觉与交付

开发严格采用 TDD：先为领域检索、请求校验、演示降级、响应归一化和关键 UI 状态编写失败测试，再实现最小功能。单元测试验证角色和产品映射、关键词检索、风险意图、历史裁剪与错误映射；组件测试验证角色切换、建议问题、消息提交、附件移除、加载与错误状态；集成测试验证 API 在有无模型配置时的契约；构建后测试直接调用 Worker 验证页面和 API。

视觉方向为“精密工程工作台”：暖白底色、深石墨文字、克制的橙色动作色、大面积留白、细密网格与清晰的技术标签。避免通用 AI 产品常见的紫色渐变、巨大营销标题和过度圆角。首页首屏直接让用户开始任务，产品家族以结构图式卡片呈现，来源和风险标签具有一致的视觉语义。

交付包含可运行源码、环境变量示例、官方来源清单、开发与部署说明、测试脚本和架构说明。完成门禁依次为 TypeScript、Lint、单元/组件测试、生产构建、构建后 Worker 测试、移动端截图检查与可访问性检查。若缺少真实模型配置，自动化会验证演示模式和上游适配器契约，README 会明确说明如何启用真实问答。
